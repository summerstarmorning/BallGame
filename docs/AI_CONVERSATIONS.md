# AI 对话记录

以下记录按课程要求整理为 3 次有代表性的 AI 协作对话。内容来自项目开发中的真实问题类型，并整理成可提交版本：每次都包含“问题、AI建议、人工取舍、落地结果”。

## 对话 1：冲量式碰撞与挡板自由度

**用户**：原来的打砖块碰撞只是把小球速度取反，手感很死。现在挡板已经支持上下移动，怎样让挡板运动真正影响小球反弹？

**AI**：可以把球与挡板的碰撞改成基于法线的反射：先用圆与矩形最近点计算碰撞法线和穿透深度，再把挡板速度按一定比例加入相对速度。这样挡板横向移动会改变水平反弹，纵向移动会改变垂直反弹，但比例不能太大，否则球速会失控。建议在反射后限制最低垂直速度，避免小球进入几乎水平的死循环。

**人工取舍**：保留了 AI 给出的“相对速度 + 法线反射”思路，但没有完全按真实物理模拟实现，而是设置了 `kPaddleHorizontalTransfer`、`kPaddleVerticalTransfer` 和最低垂直速度比例，让玩法更稳定。

**落地结果**：`src/GamePlay.cpp` 中的 `HandleBallPaddleCollision()` 会按挡板运动注入冲量，`ConstrainBallTravelDirection()` 避免死角轨迹。路演中可作为“自由度和仿真物理模型”的亮点说明。

## 对话 2：砖块碰撞性能优化

**用户**：关卡砖块数量变多后，每一帧让球和所有砖块逐个检测不够优雅。怎么做一个适合课堂项目展示的性能优化？

**AI**：可以使用空间划分。把游戏区域分成固定大小网格，每块砖登记到覆盖的格子里。小球检测时先根据圆形范围查询附近格子，拿到候选砖块，再做精确的圆与矩形碰撞。这样实现难度比四叉树低，解释成本低，也能配合 benchmark 展示优化效果。

**人工取舍**：选择固定网格而不是四叉树，因为砖块基本静态、分布规则，固定网格更容易维护和讲清楚。为了避免重复候选，增加了 query stamp 标记。

**落地结果**：`include/Performance/BrickSpatialGrid.hpp` 和 `src/Performance/BrickSpatialGrid.cpp` 实现空间网格；`Game::HandleBallBrickCollision()` 先查询候选，再做精确检测；`collision_benchmark` 可用于性能验证。

## 对话 3：网络同步与 AI 协作记录整理

**用户**：网络联机 Demo 中，为什么不直接把画面状态用 JSON 发给客户端？客户端看到的球为什么可能有一点延迟？

**AI**：实时游戏同步更适合“权威主机 + 输入上行 + 快照下行”。主机负责真实游戏状态，客户端只发输入并渲染收到的状态。快照可以用结构化二进制包传输，包更小、解析更快；客户端故意用约 100ms 的插值缓冲，在两个快照之间平滑过渡，因此本地看到的画面会略晚但更稳定。

**人工取舍**：保留权威主机和客户端插值，二进制包只用于 Demo 说明，不强行接入主游戏流程，避免影响单机核心体验。

**落地结果**：`src/Networking/` 中保留网络包和会话封装，`network_sync_demo` 可展示同步思路；README 中把它定位为工程扩展模块，而不是主游戏的必要依赖。

## 简短总结

AI 在本项目中的作用不是直接替代实现，而是帮助拆解问题、比较方案、生成初稿和解释复杂模块。最终代码仍经过人工选择、调试和项目化整理。
